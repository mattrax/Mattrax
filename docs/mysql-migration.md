# PostgreSQL → MySQL migration (feasibility spike)

Status: **staged spike, not mergeable as-is.** The application schema, Drizzle
runtime, Hyperdrive wiring and query rewrites are complete and typecheck/build.
The auth persistence layer is blocked on an upstream package gap and is enabled
here only through two `pnpm` patches.

This branch is intentionally a draft PR. Do not merge it until the upstream
blocker below is resolved and the migration has been exercised against a real
MySQL 8 database behind Hyperdrive.

## Primary blocker: Yielded Auth has no composed MySQL adapter

`@yielded/auth-persistence-drizzle@0.1.0-beta.47` ships `/Mysql2`, but unlike
`/Postgres` and `/SqliteBun` it does **not** export `AuthPersistence`:

- `src/Mysql2.ts` exports the explicit factories (`makePasswordPersistenceServices`,
  `makeProofPersistenceServices`, `makeAuthenticationAuthorityServices`,
  `makePendingAuthenticationServices`, `makeStatefulSessionServices`,
  `makeSessionCleanupServices`, `makeSessionStepUpServices`,
  `makePasswordRegistrationServices`, identity services, …).
- `src/Postgres.ts` additionally exports `AuthPersistence` built from
  `createPersistence(...)` plus `managed`/`map`/`layer`/`migrationsLayer`.
- `@yielded/auth-persistence/src/internal/persistence.ts` only recognizes `pg`
  and `sqlite` in the composed layer's `onDialectOrElse` check
  (`Use an explicit adapter for this SQL dialect` for MySQL).

Mattrax's auth composition is written against the composed API:

```ts
export const AuthPersistenceConfig = AuthPersistence.make(AuthDefinition);
export const authStorage = AuthPersistenceConfig.managed({ ... });
// ...
const PersistenceLive = AuthPersistenceConfig.layer.pipe(
  Layer.provide(AuthPersistenceConfig.Config.layer(authStorage)),
  Layer.provide(ProvisioningLive),
);
```

It cannot be expressed with the explicit MySQL factories without hand-wiring
the full service graph and the tables those factories expect. That means:

- defining MySQL physical tables for all generated auth roles,
- building every typed mapping (`IdentityTables`, `PasswordPersistenceMapping`,
  session/pending/proof mappings, registration mapping),
- reproducing transaction/coordinator ownership (`SqlNativeCommit`,
  `CurrentSqlCommit`, lifecycle hooks) and registration provisioning,
- keeping subject/credential/session semantics identical to the Postgres path.

That is a re-architecture of the auth integration, not a mechanical port. It
should live upstream in `@yielded/auth-persistence-drizzle` (or a first-party
fork), not in Mattrax.

### Workaround in this spike

Two `pnpm` patches make the composed path work:

1. `patches/@yielded__auth-persistence@0.1.0-beta.47.patch`
   - Adds `mysql: () => "mysql"` to the composed layer's dialect detection.
2. `patches/@yielded__auth-persistence-drizzle@0.1.0-beta.47.patch`
   - Adds `dist/internal/drizzle-mysql.mjs` (+ `src/internal/drizzle-mysql.ts`):
     a MySQL `Backend` for `createPersistence(...)`.
   - Exports `AuthPersistence` from `/Mysql2` (with `migrationsLayer` using
     `drizzle-orm/effect-mysql2/migrator`).

The MySQL backend maps generated storage columns as follows:

- keyed `text` → `varchar` (`value` = 320, other ids = 191) so MySQL can index
  them under the 3072-byte InnoDB key limit for `utf8mb4`;
- non-keyed `text` → `text`;
- managed `integer` → `bigint` (`mode: "number"`) because auth stores epoch
  milliseconds;
- `boolean` → MySQL `boolean` (`tinyint(1)`).

These patches are a proposal for the upstream change, not something to carry
indefinitely. They also need upstream review for:

- **Isolation/transaction ownership.** The composed layer falls back to
  `sql.withTransaction` for MySQL. The explicit MySQL adapters instead use
  `mysqlNativeCommit` (reserved connection, one-shot `READ COMMITTED`) for
  authority/session workflows. The composed MySQL path therefore runs at
  MySQL's default isolation (`REPEATABLE READ`). This must be validated against
  concurrent sign-in/session-revocation tests, or the composed backend needs a
  `nativeCommit` hook so it can use the same owner as the explicit adapters.
- **Storage validation at runtime.** `validateStorageBatch("mysql", ...)` queries
  `information_schema`; generated index lengths/types must match or the first
  auth operation fails with `PersistenceConfigurationError`. This has not been
  exercised without a live server.
- **Key length for future strategies.** OAuth/passkey storage can generate
  composite keys that exceed MySQL's 3072-byte limit (for example
  `oauthConnectedGrants(moduleId, subjectId, profileKey, identityKey)`). Those
  strategies need a different key-hashing design before MySQL can be a general
  adapter. They are not generated for Mattrax today (password + stateful
  sessions only).

Without the patches the branch does not typecheck: `/Mysql2` has no
`AuthPersistence`, no `managed`, no `Config`, no `layer`.

## MySQL-specific changes and caveats

### Schema

- `text` primary/unique/index keys → `varchar` (MySQL cannot index `TEXT`
  without a prefix length). Application tables use `varchar(255)`; emails use
  `varchar(320)`; auth generated tables use 191/320 as above.
- `timestamp(..., { mode: "date" })` → `datetime(..., { mode: "date", fsp: 3 })`.
  MySQL `TIMESTAMP` is limited to 1970–2038 and has implicit auto-update
  semantics; `DATETIME(3)` preserves milliseconds and avoids both.
  `timezone: "Z"` is set on the mysql2 pool so reads/writes stay UTC.
- `jsonb` → `json` (`configuration.data`, `scep_ca.private_key_jwk`).
- `serial` → `int().autoincrement()` (`scep_ca.id`). An explicit `id: 1` insert
  still works.
- `gen_random_uuid()::text` default removed from `user.auth_revision`.
  MySQL rejects non-deterministic defaults; provisioning already supplies a
  UUID. Any future direct `user` insert must set `authRevision`.

### Queries

- `onConflictDoNothing()` → `.ignore()` **before** `.values()` (MySQL
  `INSERT IGNORE`). Note `INSERT IGNORE` also suppresses other ignorable
  errors, not just duplicate keys.
- `onConflictDoUpdate({ target, set })` → `.onDuplicateKeyUpdate({ set })`.
  MySQL infers the conflict target from any primary/unique key, so the explicit
  target disappears.
- `DELETE ... RETURNING` → tenant-scoped `findFirst` then `delete`
  (`deleteGroups`, `deletePolicies`). This adds a read and is not atomic; if
  that matters, use an affected-row count from the mysql2 result instead.

### Cloudflare Hyperdrive

`apps/api/src/index.ts` uses the fields Hyperdrive exposes for MySQL:

```ts
MysqlClient.layer({
  host: env.HYPERDRIVE.host,
  port: env.HYPERDRIVE.port,
  username: env.HYPERDRIVE.user,
  password: Redacted.make(env.HYPERDRIVE.password),
  database: env.HYPERDRIVE.database,
  poolConfig: { disableEval: true, timezone: "Z" },
  disablePreparedStatements: true,
});
```

`url` must not be used: `@effect/sql-mysql2` ignores `poolConfig` when `url` is
set, which would silently drop `disableEval`. `disablePreparedStatements` is
required because Hyperdrive rejects MySQL `COM_STMT_PREPARE`.

`apps/api/cloudflare.config.ts` local-dev `connectionString` now uses
`mysql://…`; that dev-only string is the only place a connection URL remains.

### Migrations / data

The Postgres migration under `apps/api/migrations/` was deleted and replaced
with the generated MySQL migration. There is **no data migration** from
Postgres. A real rollout needs an export/transform/import step for every table
(notably `jsonb` payloads, boolean representation, timestamp precision, and
generated auth identifiers/sessions). Treat that as separate work.

## What would make this mergeable

1. `@yielded/auth-persistence-drizzle` publishes `/Mysql2` with the composed
   `AuthPersistence` (or Mattrax pins a reviewed fork).
2. The composed path uses the same MySQL transaction/isolation owner as the
   explicit adapters, or concurrency tests prove the `withTransaction` fallback
   is safe.
3. `validateStorageBatch("mysql", ...)` passes against the generated schema on a
   live MySQL 8 database, including index-length checks.
4. A real Postgres → MySQL data migration exists, or the rollout is explicitly
   a greenfield/parallel-run cutover.
5. Hyperdrive MySQL is exercised in a deployed preview (text protocol, no
   prepared statements, `disableEval`).
