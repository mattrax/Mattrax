# User-scoped policies

Mattrax has two independent policy channels. A configuration belongs to one of them, and it
is never copied to the other.

| Channel    | Delivery                                            | Applies to                      |
| ---------- | --------------------------------------------------- | ------------------------------- |
| **Device** | Apple device channel, Windows OMA-DM, Android AMAPI | Every user of the device        |
| **User**   | Apple user channel (macOS 13+, Shared iPad)         | One authenticated, linked login |

This is what prevents the old ambiguity where a user-assigned policy silently became
device-wide. Device settings still follow the device; user settings follow the person who
signed in.

## Marking scope

Every configuration carries `scope: "device" | "user"` (default `device`). The policy editor
exposes it per configuration: a **Scope** control sits beside each Apple profile and the
Windows OMA-URI. Settings generated by the policy designer are device-scoped, because the
designer builds one artifact per platform and Apple decides user scope per payload; add
user-scoped settings in the policy editor. The API accepts a `configurationScopes` map
alongside `configurations`, and older clients that omit it keep device scope.

Scope is a claim, not a bypass: the API validates that the platform can honour it.

| Kind                                              | User scope                                                                                                                                                                                          |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mttx.apple.custom.*`                             | Requires `PayloadScope: User` in the mobileconfig. Signed profiles cannot be inspected, so they are device-only.                                                                                    |
| `mttx.apple.declaration.*`                        | Only declaration types Apple documents with a `user` macOS scope (for example `com.apple.configuration.app.settings`, `com.apple.configuration.legacy`, `com.apple.configuration.safari.settings`). |
| `mttx.apple.device`, `certificate`, `application` | Rejected. These are device credentials or imperative device installs.                                                                                                                               |
| `mttx.windows.custom.*`                           | Every OMA-URI must start with `./User/`. Windows applies it to every user on the device; there is no per-login channel.                                                                             |
| `mttx.android.policy.*`                           | Rejected. AMAPI assigns a policy to a device (or work profile), not an end user.                                                                                                                    |

## Resolution

The resolver is scope-aware:

- The **device channel** resolves only `device` configurations. Device and group assignments
  contribute, and user assignments still contribute device-wide for compatibility (they are
  evaluated as before, but only their device-scoped configurations are delivered).
- A **user channel** resolves only `user` configurations for one directory user. Device and
  group assignments contribute their user-scoped settings to every user of the device; the
  user's direct and directory-group assignments contribute only to that user.
- Device scope beats user scope for the same kind. Direct beats group, then priority,
  `updatedAt` and id decide ties, exactly as on the device channel.

The resolved set is annotated with `channel`, so a consumer cannot accidentally serve one
channel's configuration through the other.

## Apple user channel

A user channel is created by Apple's `UserAuthenticate`/`TokenUpdate` handshake and is
identified by `UserID` (the local account GUID) plus the short and long name Apple reports.
Delivering user policy requires more:

1. The channel must be **bound to a directory person**. Unbound channels still check in,
   receive commands and push, but are told they have no declarations.
2. The bound channel receives its own declaration set: per-user activation groups,
   configuration declarations, server tokens and a stored `ddmDeclarationsToken` on
   `device_apple_user`.
3. A check-in returns `DdmSync` only for a bound channel with declarations (or one that had
   them previously, so removals sync). The device channel is never asked to sync user scope.
4. Declaration status reports are written to `device_user_declaration`, not the device
   inventory. A user channel cannot acknowledge a device declaration and vice versa.
5. The declaration endpoint serves only identifiers in that user's resolved set. There is no
   fallback to device declarations.

Legacy payloads are delivered through `com.apple.configuration.legacy` declarations on the
user channel, so a user-scoped mobileconfig installs in that login's context. macOS 13 or
later is required for declarative management; older logins are skipped by the same OS-scoping
the device channel uses.

## Binding an identity

Mattrax records the binding on `device_apple_user`:

- `directoryUserId` — the tenant directory person
- `identitySource` — `manual`, `certificate` or `managed-apple-account`
- `identityUpn` — the IdP subject the binding was checked against
- `identityVerifiedAt` — when that check happened

The device page shows each channel's binding and lets an operator link it to a directory
person (`PUT /v1/tenants/:tenantId/devices/:id/apple-users/:userId/identity`). Binding clears
the old declaration set and wakes the channel so it recomputes policy. Unbinding clears the
binding and the per-user declaration rows.

### Managed Apple Accounts (Shared iPad)

Shared iPad never authenticates the person using it: Apple sends the same sentinel `UserID`
for every login. `UserShortName` carries the Managed Apple Account identifier, which is an
email address, so that is the channel key and the correlation input.

When a Shared iPad channel registers, Mattrax looks for a directory person in the tenant with
exactly that email and binds the channel as `identitySource: "managed-apple-account"`. The
match is exact and never overrides a manual or certificate binding; an account that is not in
the directory stays unbound and receives no user policy. Only the Managed Apple Account
identifier Apple itself issued is used, so a device cannot choose someone else's identity.

### Roadmap: certificate identity

The automated macOS source is a **per-user certificate**. The user completes an IdP sign-in
from a user-scoped profile, the server mints a one-time SCEP challenge bound to the device and
Apple user, and the issued certificate carries the verified UPN in its subject/SAN. The
channel that installs that certificate becomes `identitySource: "certificate"`. That is
stronger than the Managed Apple Account email match and is the intended default for macOS
fleets.

Until it lands, a channel with no binding receives no user policy. That is deliberate:
silently falling back to "every linked user" is the behaviour this feature replaces.

## Windows and Android

- **Windows** has user-scoped CSP paths but no per-login MDM channel. A user-scoped Windows
  configuration is delivered through OMA-DM with its `./User/` paths and applies to every
  user on the device. The editor says so; the API rejects `./Device/` URIs in a user-scoped
  configuration.
- **Android** has no equivalent: AMAPI assigns one policy to a device (or its work profile).
  User scope is rejected rather than silently widened to the device.
